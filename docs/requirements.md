# 需求与约束

状态：M1-A 基线。本文区分产品需求、当前阶段已接受决策与仍未确定事项。

## 已确认需求

- Aster 是两人共同开发、用于学习和长期演进的智能体客服项目。
- 主要开发环境是 Windows + WSL2 Ubuntu；项目需要容易理解、运行和认领任务。
- Aster Core 不直接依赖 QQ、企业微信、钉钉等具体平台 SDK。
- 消息渠道通过统一边界接入；接收/发送职责、运行位置和通信协议仍需验证。
- Agent、RAG、工具/MCP、自动化、工单与渠道不能堆入单一 Service 或路由。
- 只为当前变化点建立抽象；没有真实需求或第二实现时不设计通用框架。
- 每次只推进一个可独立验收的小里程碑，并同步计划与开发日志。

## 当前阶段已接受决策

- Python 模块化单体作为当前实验基线；这是可逆选择，不代表永久技术栈或部署形态。
- M1 使用进程内 Fake/Console Adapter 验证渠道边界。
- 当前插件化只要求 Core 不依赖具体平台 SDK，并存在清晰的渠道载荷转换边界。
- 多租户 SaaS 方向保持开放；当前既不主动封死演进路径，也不预建租户、权限或复杂基础设施。

## M1 非目标

- M1-A 不实现业务代码或初始化后端框架；M1-B 只有另行确认后才能开始。
- 不创建数据库模型、真实消息渠道、LLM/RAG/MCP、Agent 或自动化实现。
- 不增加 Docker Compose、Redis、RabbitMQ、Kafka、Temporal 等基础设施。
- 不建立动态插件发现、独立插件进程、HTTP/WS 插件协议、第三方 SDK、插件市场或完整多服务目录。

## 关键不确定项

- Python/模块化单体何时需要重新评估，以及未来 Web 框架选择。
- 真实渠道出现后是否需要进程隔离；这不是固定 Roadmap 项。
- Agent 编排已确定为最小自建（M2/M4 落地：薄应用层 + 单模块 provider 边界）；RAG 与工具调用是自建、用库还是对接外部平台仍开放。
- 会话、消息、客户数据何时需要数据库级持久化；M3 已用单 JSON 文件验证最小会话持久化与重复投递幂等，数据库选型仍开放。
- Aster 是否可能作为多租户 SaaS 或可再分发产品，这会影响许可证与租户边界。

## 待验证假设

- 两人团队在早期能从单一进程和单一语言获得最低认知/调试成本。
- 一个最小规范消息对象足以隔离核心逻辑与首个 Fake/Console 渠道。
- 在可靠异步、吞吐或跨进程故障隔离需求出现前，内存调用比消息队列更合适。
- 首版文本消息契约可以在不加入通用 metadata 和多媒体抽象的前提下，保留后续演进空间。

## 未来可能方向

智能对话、意图/情感识别、RAG、工具与 MCP、人工转接、长期记忆、真实渠道、自动化、工单和报表均是未来候选，不是当前承诺。
