# Aster 架构建议

状态：**部分已接受，部分仍为建议**

日期：2026-09-03

Python 模块化单体和 M1 进程内 Fake/Console Adapter 已在 [ADR-0001](../adr/0001-experimental-baseline.md) 中接受。M2 对话应用层与 M3 JSON 文件持久化已作为最小实验落地；LLM provider、Web 框架及进程外边界仍是建议或开放问题。

本文保留整体方案与重评条件；只有 ADR-0001 明确列出的内容属于已接受决策。

## 背景与约束

Aster 要同时容纳客服会话、AI 编排、知识检索、工具和多个消息渠道，但当前只有两名贡献者，且目标是学习与长期演进。首要矛盾是保持边界清晰，同时避免用多进程、插件框架和中间件提前支付复杂度。

## 推荐方案

当前以 **Python 模块化单体 + 可迁移的外部适配边界** 起步：

1. **已接受**：当前实验采用单一仓库、Python 模块化单体和单一核心进程；真正需要 HTTP 时再确认 Web 框架。
2. **已接受**：核心只认识规范化的会话、消息和处理结果，不认识 QQ/企微/钉钉 SDK 类型。
3. **已接受**：M1 的 Fake/Console 渠道在进程内完成接收和发送；暂不做动态插件加载或进程外协议。
4. **当前建议**：M2 用最小 Agent 对话链路验证对话应用层，再决定 LLM provider 等窄边界。
5. **当前建议**：M3 才验证会话持久化；在可靠异步需求出现前不引入 MQ。

建议的依赖方向是：

```text
Channel adapter -> conversation application flow -> conversation/message rules
                                      |
                                      +-> response strategy (initially deterministic)

Infrastructure implements only the boundaries required by the current milestone.
Core/application code never imports a platform SDK.
```

这不是要求现在创建同名目录、接口或类；结构应随每个纵向实验按最少文件落地。

## 会话与消息的最小概念

在设计数据库前，实验至少需要验证这些语义：

- `Conversation` 关联一个渠道实例和该渠道的外部会话标识；
- `Message` 有 Aster 内部标识、外部消息标识、方向、内容、时间和可选元数据；
- Adapter 负责平台载荷与规范消息互转，以及把规范回复送回平台；
- 外部标识必须保留，以便后续幂等、回执和故障排查；
- 原始载荷是否完整持久化涉及隐私与审计，暂不决定。

Chatwoot 的 channel/inbox/conversation/message 分层可作为语义参考，但 Aster 不复制其模型或代码。

## 渠道边界的演进规则

第一版让 Adapter 同时承担接收转换和发送转换，是为了用一条链路验证双向契约。以下任一证据出现时，重新评估进程外 Adapter：

- 平台 SDK 与 Core 依赖或运行时冲突；
- 插件崩溃不可接受地影响 Core；
- 插件需要独立语言、发布周期或扩缩容；
- 允许非可信第三方开发/运行插件；
- 多个真实插件证明需要稳定公共 SDK。

届时优先验证版本化 HTTP webhook/command 协议；需要长连接或流式状态时比较 WebSocket；需要可靠排队、削峰和 worker 重试时才比较消息队列。协议应包含能力声明、版本、关联 ID、幂等键和可分类错误，但仅在实验需要时逐项加入。

## Agent、RAG 和工具边界

建议自建的不是“通用 Agent 框架”，而是一层很薄的客服编排：读取会话上下文，选择当前回复策略，调用需要的能力，并生成可审计结果。

- LLM provider 负责模型调用细节，不拥有客服流程。
- RAG 负责检索并返回证据，不直接发送渠道消息。
- 工具执行负责 schema 校验、权限、确认和执行记录。
- 人工转接属于会话状态变化，不应藏在模型 provider 中。

Dify/RAGFlow 可在后续通过 API 做替换实验；只有当状态图、暂停恢复、检查点或观测成为明确验收要求时，才比较 Agent 框架。当前不 Fork 大型平台。

## 已知缺点

- 单进程无法隔离平台 SDK 崩溃，也不能独立扩缩容。
- Python 动态类型和异步混用需要类型检查、清晰边界和测试纪律。
- 先内存后持久化会产生一次有意的小重构。
- 自建薄编排层存在逐渐膨胀成自研框架的风险，必须用里程碑范围约束。
- 延迟选择 HTTP 框架和数据库会推迟部分工程化，但避免在需求不足时锁定方案。

## 当前假设

- 近期只有 Fake/Console 渠道，没有需要隔离的真实平台 SDK。
- 首个实验的消息量和可靠性目标允许单进程、内存状态。
- 团队愿意以 Python 为共同后端语言，并接受在需要 HTTP 时再选框架。
- Aster 的多租户 SaaS/再分发形态尚未确定，因此不把受限许可证项目纳入核心。

## 固定的近期验证顺序

1. **M1 核心消息契约**：Fake/Console 入站转换为规范消息，经确定性处理器得到回复，再转换为出站。（已完成）
2. **M2 最小 Agent 对话链路**：已按最小对话应用层落地——会话状态加依赖轮次的确定性回复；真实模型调用因缺少 API key 与 provider 决定尚未开始。
3. **M3 会话持久化**：已用单 JSON 文件验证重启恢复、重复投递幂等和最小会话历史；数据库选型仍开放。

进程外 Channel Adapter 不进入固定 Roadmap。只有 SDK/语言冲突、崩溃隔离、独立发布扩缩容或非可信第三方代码等条件出现后，才提出专门实验。

## 重新评估条件

- 同时接入两个真实渠道后发现规范消息丢失关键能力；
- SDK 冲突、崩溃或安全边界要求进程隔离；
- 需要横向扩展、可靠异步重试或长任务；
- 客服后台、复杂权限和关系数据成为近期核心，可能使 Django 或外部 Chatwoot 更合适；
- Agent 流程需要持久化状态图、暂停恢复或复杂观测；
- 产品明确转向多租户 SaaS、白标或可再分发方案，需重做许可证与租户架构评审。
