# ADR-0001：当前实验基线与渠道边界

- 状态：Accepted
- 日期：2026-09-03
- 范围：当前实验阶段，可逆

## 背景

Aster 由两人共同开发，当前要尽快验证核心产品纵向链路，同时保持 Core 与具体消息平台解耦。Python、单体形态、渠道运行方式和多租户方向此前均未确认。

## 可选方案

- Core 采用 Python 或在 Node.js/Go 等语言中重新选择。
- 采用简单单体、模块化单体、Core + 外部 Adapter 或多服务。
- M1 Adapter 在进程内、独立子进程或独立 HTTP/WS 服务运行。
- 现在建立多租户基础设施，或保持方向开放并推迟实现。

## 选择结果

1. Python 模块化单体作为当前实验基线，不代表永久技术栈或部署形态。
2. M1 使用进程内 Fake/Console Adapter。当前“插件化”只要求 Core 不依赖具体平台 SDK，并存在清晰的渠道载荷转换边界。
3. 当前不建设动态插件发现、独立插件进程、HTTP/WS 插件协议、插件市场或第三方插件 SDK。
4. 多租户 SaaS 保持开放；设计不得有意封死未来演进，但不为假设中的 SaaS 预建租户系统、权限平台或复杂基础设施。

## 选择理由

- 复用团队 Python 经验，以最低运行和调试成本验证真实链路。
- 模块化单体可以表达 Core/Adapter 依赖方向，同时避免过早承担分布式协议和部署成本。
- Fake/Console Adapter 足以回答 M1 的契约问题，无法为进程隔离的额外成本提供当前证据。
- 多租户仍是产品问题；推迟实现可以避免把未知商业形态固化进早期模型。

## 已知代价

- 单进程不能隔离渠道 SDK 的崩溃、依赖冲突或资源消耗。
- Python 与模块化单体仍需要测试和依赖方向纪律。
- 若产品明确转向多租户，早期数据模型可能需要迁移。
- 推迟公共插件协议意味着未来可能进行一次有意的边界升级。

## 重新评估条件

- 真实平台 SDK 产生语言/依赖冲突或不可接受的崩溃影响；
- 渠道需要独立发布、扩缩容或运行非可信第三方代码；
- 多个真实 Adapter 证明需要稳定的第三方 SDK 或版本化协议；
- 团队发现 Python 显著阻碍关键渠道或产品链路；
- 产品明确采用多租户 SaaS、白标或再分发模式。
